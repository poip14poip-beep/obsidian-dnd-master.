# План: облачное хранение через приватную схему `obsidian` (только проектирование)

Статус: ничего не подключено. Код, миграции и функции на этом этапе не создаются.

## Что проверено в текущем коде
- `src/domain/types.ts`: 11 коллекций в `ObsidianCollections` (`sources`, `canon_facts`, `world_state`, `player_character_state`, `npcs`, `factions`, `locations`, `timeline_events`, `turn_drafts`, `session_log`, `audit_log`), `BackupEnvelope`, `IntegrityReport`.

- `src/store/obsidian-store.tsx`: единый store, commit хода локально.
- `src/lib/supabase-auth.ts`: только publishable key, `service_role`/`sb_secret_` запрещены во фронтенде; `.from(` в `src/` не используется.

## Не проверено (нужно до реализации)
- Точный список 13 таблиц `obsidian`, колонки, PK/FK, наличие `owner_id`, RLS, индексы.
- Сигнатура и тело `obsidian.commit_turn(uuid)`: что значит uuid (draft_id? campaign_id?), что возвращает, какие исключения, использует ли `auth.uid()` или `auth.jwt()`, `SECURITY DEFINER`/`INVOKER`, `search_path`.
- Текущие grants на схему (ожидаем: нет `USAGE` для `anon`/`authenticated`).
- Первый шаг реализации: read-only интроспекция (`information_schema`, `pg_proc`, `pg_policies`) с выдачей отчёта; без неё маппинг коллекций на таблицы не фиксируется.

## Архитектура

```text
Браузер (JWT пользователя, publishable key)
   │  POST /functions/v1/obsidian-api  (Authorization: Bearer <user JWT>)
   ▼
Edge Function obsidian-api  (verify_jwt = true)
   1. auth.getUser(jwt) через клиент с anon key -> user.id (единственный источник owner_id)
   2. валидация тела (zod), отклонение любых owner_id/user_id в теле
   3. service client (SUPABASE_SERVICE_ROLE_KEY из env функции)
   4. rpc в public-обёртки, передавая p_actor = user.id
   ▼
public.obsidian_api_* (SECURITY DEFINER, EXECUTE только service_role)
   - set_config('request.jwt.claims', {sub, role:'authenticated'}, true)  -- локально в транзакции
   - вызов obsidian.* / obsidian.commit_turn(...)
   - фильтр по owner_id = p_actor
```

Почему Edge Function, а не серверные функции TanStack: проект использует внешний Supabase, и Lovable Secrets не позволяют хранить ключи внешнего проекта с префиксом `VITE_`; `SUPABASE_SERVICE_ROLE_KEY` естественно доступен в окружении Edge Function этого же проекта и никогда не попадает в бандл. Альтернатива (серверные функции TanStack + секрет `OBSIDIAN_SERVICE_ROLE_KEY`) возможна, но добавляет хранение service key в окружении Lovable — оставить как запасной вариант на решение пользователя.

## Передача проверенного subject в `auth.uid()`
- `auth.uid()` читает `current_setting('request.jwt.claim.sub')` / `request.jwt.claims->>'sub'`.
- Обёртка выставляет оба через `set_config(..., true)` (is_local = true) в начале своей транзакции; PostgREST выполняет RPC в одной транзакции, поэтому значение живёт ровно до её конца и не протекает в пул соединений.
- `p_actor` приходит только из Edge Function после `auth.getUser`; обёртка недоступна `anon`/`authenticated` (`REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated; GRANT ... TO service_role`).
- Внутри обёртки: `SET search_path = ''`, все имена полностью квалифицированы (`obsidian.commit_turn`).
- Альтернатива без подмены claims: обёртка вызывает внутреннюю `obsidian.commit_turn_as(p_actor uuid, ...)`. Требует изменения существующей функции — только если пользователь разрешит.

## Перечень эндпоинтов (одна Edge Function, маршрутизация по `action`)
| action | RPC-обёртка | Назначение |
|---|---|---|
| `bootstrap` | `public.obsidian_api_get_snapshot(p_actor)` | все сущности владельца + версии/checksum |
| `list` | `public.obsidian_api_list(p_actor, p_collection)` | одна коллекция (белый список имён) |
| `upsert` | `public.obsidian_api_upsert(p_actor, p_collection, p_payload, p_expected_version)` | создание/изменение с оптимистичной блокировкой |
| `save_draft` | `public.obsidian_api_save_draft(p_actor, p_draft)` | черновик хода без commit |
| `commit_turn` | `public.obsidian_api_commit_turn(p_actor, p_draft_id)` | вызов `obsidian.commit_turn(uuid)` атомарно |
| `verify` | `public.obsidian_api_verify(p_actor, p_ids)` | серверный read-back и checksum для сверки |

Запрещено как API: удаление/правка записей `session_log` и `audit_log` (append-only), смена `owner_id`, массовая перезапись чужих данных.

## Изменения во фронтенде (позже)
- `src/lib/obsidian-api.ts`: тонкий клиент, `supabase.functions.invoke('obsidian-api', ...)` с JWT текущей сессии.
- Store: режим «локально» остаётся по умолчанию; облачный режим включается только после успешного `bootstrap`. После `commit_turn` — `verify` и сравнение с локальным payload; при несовпадении — ошибка, без сообщения об успехе.
- Индикатор синхронизации показывает реальный статус ответа сервера, без имитации.

## Риски и неразрешённые места
1. Подмена claims: любой обладатель service_role может действовать от имени любого пользователя — допустимо только потому, что service_role и так обходит RLS; ключ строго в env функции.
2. Если `commit_turn` использует `auth.role()` или `auth.jwt()` с другими полями — claims надо формировать полнее; требует чтения тела функции.
3. Если `commit_turn` — `SECURITY INVOKER` с RLS, вызов от service_role обойдёт RLS; owner-фильтрация должна быть явной в функции.
4. Отображение 11 коллекций на 13 таблиц неизвестно (возможно отдельные таблицы ревизий/знаний NPC).
5. Транзакционность гарантируется только внутри одного RPC; несколько `upsert` подряд не атомарны — помечать это в UI.
6. Миграция существующих локальных данных: только явным действием пользователя, с предпросмотром; не автоматически.
7. Конфликты версий между устройствами: нужна колонка версии/`updated_at`; если её нет — требуется миграция.
8. Хранение service key при альтернативе через TanStack-серверные функции.
9. Rate limiting и размер payload в Edge Function.

## Минимальные тесты
- Edge Function: без JWT -> 401; поддельный JWT -> 401; `owner_id` в теле -> 400; неизвестная коллекция -> 400.
- SQL: `anon`/`authenticated` не могут `EXECUTE` обёртки и не имеют `USAGE` на `obsidian`.
- SQL: после обёртки `current_setting('request.jwt.claims', true)` в новой транзакции пуст (нет утечки).
- Изоляция: пользователь A не читает и не меняет данные B.
- `commit_turn`: повторный вызов для того же черновика не создаёт второй ход; номера последовательны; ошибка внутри откатывает всё.
- Фронтенд: при несовпадении read-back показывается ошибка; `service_role`/`sb_secret_` отсутствуют в бандле (существующий тест).
